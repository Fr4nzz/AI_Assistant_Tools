# Review workflow

Use this when the user comments on a draft or wants to approve changes. Two modes have worked.

## Bracketed comments on a whole document

This is how the user reviewed the progress report: comments in square brackets inline in a Word or Google document, sometimes dozens per version.

1. Extract every comment with its context and give it a stable id (C01, C02 …). Keep the raw wording.
2. Sort each comment: a style change, a content or analysis request, a factual correction, or a question for the user alone ("just for me, not for this document").
3. Read a question as a request unless it is marked as personal. "Isn't this obvious?" usually means delete, and one pushback with a reason is welcome. "What do you mean by X?" means rewrite X so the question cannot arise.
4. Apply the changes. Mirror them in every language version.
5. Answer personal questions and explain any analysis in the reply, not in the document.
6. Push back at most once per comment, with evidence the user can check: a source line, a number, a DOI. When the user repeats a style or scope comment, comply. Factual pushback (a correct DOI, a number that contradicts the suggested word) can hold.
7. Route analysis that needs new work to its owner, and say in the decision table that it was routed.
8. Keep a decision table: id, the comment in short, the decision (applied, partly applied, pushed back, routed, answered in chat), and the changed wording. Before delivery, check that every id has a decision. The user has complained when comments were skipped.
9. Before the next version, check that each change still agrees with earlier decisions. An earlier comment stays in force unless the user reverses it.

## Paragraph by paragraph

For a manuscript the user wants to approve closely, work in small units. Show the current text, one recommended revision and a short reason tied to meaning, clarity, structure or voice. Offer alternatives only for a real choice, for example heading styles when the user dislikes the current one. Bold only the changed wording when comparison helps. Wait for the user's response before applying a phrase across the document.

## Recording preferences

An accepted edit without comment is weak evidence. Record an enduring preference when the user states it, explains it or repeats it, and add it to [comment-ledger.md](comment-ledger.md) with its strength. When later feedback conflicts with older guidance, follow the later instruction and mark the older one as superseded.
